# CLAUDE.md — Cortege

## Project overview

IBP (Indice de Biodiversité Potentielle) is a field-survey mobile app that lets ecologists record biodiversity assessments on land parcels. Observers score ten factors (A–J) in the field; the app works offline and syncs to a backend when connectivity is restored.

This is an **npm workspaces monorepo** with three workspaces:

| Package | Path | Description |
|---------|------|-------------|
| `mobile` | `mobile/` | Expo / React Native iOS + Android client. `ios/` and `android/` are generated by `expo prebuild`, not committed — native changes go in `app.json` or a plugin under `mobile/plugins/`. See `mobile/README-native.md` |
| `api` | `api/` | NestJS REST API with PostgreSQL |
| `ibp-domain` | `packages/ibp-domain/` | `@cortege/ibp-domain`: pure TypeScript IBP rules (v3.0 + v3.2), bands and the sync/public wire types, shared by api and mobile. No runtime dependencies |

The root `package.json` holds only the workspaces (`mobile`, `api`, `packages/ibp-domain`), `overrides` and a dev dependency: no runtime dependencies and no root `App.tsx` or `tsconfig.json`. Mobile runtime packages (`expo`, `react`, `react-native`) belong to the `mobile` workspace.

Other top-level directories:

| Directory | Description |
|-----------|-------------|
| `infra/` | Docker Compose files for local dev and VPS deployment |
| `docs/` | Technical architecture, API/data contracts, ADRs, product specs |
| `.github/workflows/` | CI pipeline (`ci.yml`); deployment is pull-based, see `infra/vps/` |


## Code conventions

### Formatting (`.prettierrc.json`)

- Double quotes (`"`)
- No semicolons
- Trailing commas everywhere
- 2-space indent
- 100-character line width

### Linting (`.eslintrc.json`)

- Unused variables are an **error** — prefix intentionally unused vars/args with `_` to suppress (e.g. `_event`)
- `no-explicit-any` is a **warning** — avoid `any`; use proper types or `unknown`
- `no-require-imports` is an **error** — use ES module `import` syntax only

### Naming

- React components: `PascalCase` (files and exports)
- Hooks: `camelCase` prefixed with `use` (e.g. `useSurveySync`)
- Utilities / services: `camelCase`
- Test files: co-located as `*.test.ts(x)` (unit); API integration/unit specs live in `api/test/` as `*.spec.ts`, and API E2E specs as `*.e2e-spec.ts`
- DTOs: suffix with `Dto` or `Body` (e.g. `SurveyUpsertBody`)

### TypeScript

- Prefer explicit `export type` for type-only exports
- Strict mode is on — no implicit `any`, no unchecked indexing in hot paths
- API DTOs use `class-validator` decorators for request validation

## Architecture

### Mobile (offline-first)

The mobile app is designed to work without connectivity. All survey data is persisted locally in SQLite before being synced.

**SQLite schema** (`mobile/src/storage/db.ts`, `PRAGMA user_version` migrations, currently at 5 — migration 2 adds `payload_completion`, precomputed at the four payload-write sites instead of parsed from JSON on every list read (a percentage of 14 slots, never a factor count); migration 4 puts a survey the old deadline rule had marked `expired` back to `draft`, OA-41; migration 5 adds `payload_factors_filled`, the factors filled out of ten by `countFilledFactors` (`mobile/src/app/ibp-scoring.ts`), written at the same four sites and read by Accueil's resume card and the survey detail alike):
- `local_surveys` — survey drafts with sync state, payload and the precomputed `payload_completion`
  - since phase 27 the payload also holds `survey_note` and `weather` (no new column; the schema stays at version 5)
  - since phase 30 the payload also holds `survey_route`, the route used ("Parcours utilisé": parcours, mode de relevé, surface described; no new column; the schema stays at version 5). A pull copies it, and `readSurveyRoute` (package) reads it tolerantly
- `sync_queue` — ordered queue of pending operations (upsert, delete, etc.)
- `local_attachments` — photo metadata and upload state
- `local_meta` — key/value store for app-level state
  - key `search_recents`: the 8 recent searches of the global search, cleared by `clearLocalIbpData`; the schema stays at version 5
  - key `parcel_history:<PARCEL_ID>`: the last parcel history read online (all members' submitted surveys of the parcel, at most 50, with its fetch date), written by `useParcelSurveyHistory`, read by the PDF export (the trend section prints offline from it), deleted by `clearLocalIbpData`; the schema stays at version 5
  - key `weather_point:<SURVEY_ID>`: the parcel centre used for the weather lookup of that draft, written by the parcel selection route (through `rememberPoint`, only while the weather is still empty, D-44) or derived by `useWeatherPrefill` from the cached parcel geometry (D-39), read by `useWeatherPrefill`, deleted by `clearLocalIbpData`; the schema stays at version 5
  - key `offline_layers_policy`: `base` or `all` (default `all`), set in Paramètres, Cartes; applies to future downloads; left by `clearLocalIbpData`; the schema stays at version 5

**Sync flow**:
1. User actions write to `local_surveys` and enqueue an operation in `sync_queue`
2. `useSurveySyncNetwork` (`mobile/src/hooks/survey-sync/useSurveySyncNetwork.ts`) drains the queue by calling `POST /v1/sync`; `GET /v1/sync/changes` pulls remote changes by cursor
3. Server returns results; client applies them and clears processed entries
4. Retry backoff applies on failure (max `MAX_RETRY_COUNT = 8` retries)
5. Operations that exceed the retry limit are marked `sync_blocked = 1`
6. Phase 30: a non-submitted survey whose payload has no valid `survey_route` is held on the phone, like an unnamed draft (the OA-18 model): its `survey_upsert` and `attachment_upload` rows are left out of the batch, with no request and no retry count, until a route is written (`recoverRouteBlockedDrafts` re-queues a draft the server refused with `route_required`). Already submitted surveys are never held. This is why the guided route step finalises the draft only when the parcours is accepted

**State management** — React contexts filled by one assembler, no Redux:
- `AppStateProvider` (`mobile/src/state/AppStateProvider.tsx`) is the single assembler: it calls `useSurveySync` exactly once (the 01.5 single-sync guarantees depend on this) and publishes its memoised slices through five contexts in `mobile/src/state/`:
  - session (`useSession`, plus a narrow `useAccessToken`)
  - status (`useStatus`)
  - sync actions (`useSyncActions`)
  - surveys (`useSurveys`, plus an actions-only `useSurveyActions`)
  - survey form (`useSurveyFormState`)
  - A narrow nearby-parcels context (`useNearbyParcelsState`) is split out of the form context so keystrokes do not re-render Home
- Never call `useSurveySync` anywhere else; read state through the context hooks. Action objects are stable (`useStableActions` / `useLatestCallback` in `mobile/src/state/useLatestCallback.ts`)
- `useSurveySync` (`mobile/src/hooks/useSurveySync.ts`) — sync and session orchestrator, composed of sub-hooks under `mobile/src/hooks/survey-sync/`:
  - `useAuth0Session` — authentication state and token lifecycle
  - `useLocalDataOwner` — local-data-owner gate (single-device guarantee, 01.5 WR-08)
  - `useAttachmentPreviews` — attachment preview cache
  - `useSurveySyncNetwork` — network sync operations (`POST /v1/sync`, `GET /v1/sync/changes`)
  - `useSurveySyncProfile` — profile sync
  - `useSurveySyncSurveyOperations` — survey CRUD, submit/retry/discard, attachments
- The other hooks called once each, directly by `AppStateProvider`'s `useAppController` (not nested inside `useSurveySync`):
  - `useSurveyForm` — active form state during creation/editing
  - `useSurveyList` — local survey list cache and filters
  - `useEditingDraft` — draft editing workflow
  - `useSurveyDraftPatcher` — incremental patch accumulation
  - `useGpsCapture` — device location capture
  - `useNearbyParcels` — home screen's nearby-parcel summary, published through the narrow `useNearbyParcelsState` context
  - `useWeatherPrefill`: weather lookup at the first parcel choice of a survey only (a later parcel edit changes neither the weather nor the visit time, D-44) and catch-up on reconnection or return to the foreground, for the survey time within 24 h (a draft whose visit is older shows an explanation instead of "Réessayer", D-42, `weatherVisitTooOld`); never overwrites the sky the observer set; derives the survey time of a never-stamped draft from its creation date within 24 h (D-39); published through the narrow `useWeatherPrefillState` context
- Hooks called directly by the screens that need them (not part of the single assembler): `usePublicMapExplorer` (public map, viewport bbox loading), `useParcelStatuses` (parcel selection and home), `useDebouncedValue` (map region debouncing), `useGlobalSearch`, `useSearchGroup` and `useSearchRecents` (the global search; its pure rules are in `mobile/src/app/global-search.ts` and `search-text.ts`)

**Navigation** (`mobile/src/navigation/`):
- `AppNavigation.tsx` mounts the `NavigationContainer` and picks the native or JS tab tree; stacks live in `stacks/`, tab trees in `tabs/`
- Typed through the global `ReactNavigation.RootParamList` (`navigation/types.ts`), so `useNavigation()` and `navigate` are checked without casts
- Screens are mounted with `component={XRoute}`: memoised route components in `mobile/src/navigation/routes/` read only the contexts their screen shows. The navigator tree itself carries no data
- Tabs: Accueil, Mes Relevés, Explorer, plus Rechercher: on iOS the native search tab (`role: "search"`, drawn by iOS 26 as its own button beside the bar), on Android and the JS tabs a fourth tab (`search-outline`); Compte opens from the avatar. Both mount one `SearchStack` (`navigation/stacks/SearchStack.tsx`) with `searchHome` (`SearchHomeRoute`: one field over own surveys, matched offline on the phone, community surveys and members, places and parcels; best result then grouped results) and `searchGroup` (`SearchGroupRoute`: the "Voir les N" full list, a member's surveys). The query is the route's own state, never a context. Place and parcel results open Explorer through `PublicMapFocus` kinds `place` and `parcel` (survey focus unchanged); there is one survey stack
- Survey detail (OA-46): `surveyDetail` is the summary (title and status line, weather card, score card, photos, map, four rows, survey actions, note card, one bottom button); its sub-pages are `surveyContext` ("Contexte": method, cas and the dated weather, phase 27 D-32), `surveyParcelsPage` ("Parcelles": map, parcel list, the "Parcours utilisé" card, offline map), `surveyScore` ("Facteurs IBP": sub-scores and the ten factors) and `surveyHistory` ("Historique de la parcelle": trend card with the curve of totals cut between methods, per-factor changes against the survey just before, the parcel's surveys); the survey's change log is `surveyJournal` ("Journal du relevé"), reached only from the header "…" menu of the owner's own survey (OA-124); all four in the one survey stack, reading the selected survey from the surveys context. The six pages that show the selected survey (summary, context, parcels, score, history, journal) go through `SelectedSurveyGate` (`navigation/routes/`): a loading state instead of a blank page, one list refresh, and back after 600 ms if nothing is selected; the summary screen's `beforeRemove` listener keeps the selection on a RESET (the wizard's end), and the wizard selects its new draft after the reset. Another member's survey (`communitySurvey`) opens `communityHistory` (registered in the survey stack and the Explorer stack), never the journal; the history arithmetic lives in `mobile/src/app/parcel-history.ts` and `mobile/src/app/trend-geometry.ts` (pure, tested). The data the sub-pages share comes from `useSurveyDetailData` (`mobile/src/screens/survey-detail/`)
- Route step (Phase 30, O-19): `surveyRouteGuide` (`RouteGuideRoute`, `mobile/src/screens/route-guide/`) is the mandatory fifth creation step, after the parcel map (`surveyParcels`): a few closed questions, the proposal with its reasons, and the quick path "Je connais déjà mon parcours". The new survey is finalised and sent only when the parcours is accepted; back returns to the parcel map and writes nothing. `surveyRouteChoose` (`RouteChooseRoute`) is the chooser, a form sheet on iOS and a modal on Android (parcours, mode de relevé with four presets and one chip per factor, surface described), used in `pick` mode from the step and in `edit` mode from the "Parcelles" page. Both are in the one survey stack, typed in `navigation/types.ts`. The page state is `useRouteGuideState`; the mapping from the package's codes to French is `app/route-text.ts` and `app/route-display.ts`. The route is read through `useSurveyRoute`, and the uncapped detail inputs (B `strata_cover`, F `dmh_counts` and `surface_ha`) through `useUncappedEntry`. The "Parcours utilisé" card of the "Parcelles" page (moved from Contexte on 2026-10-14; `screens/survey-detail/route/RouteSection.tsx`, also on another member's survey, read-only) and the short route label on the summary's "Parcelles" row show it afterwards; a draft without a route reads "Parcours à choisir" and cannot be finished
- Submission step (Phase 29): both "Terminer le relevé" entries (the summary `FinishBar` and the last factor page pill) only navigate to `surveyFinish { surveyId }`, a native form sheet on iOS (detents 0.65 and 1) and a modal on Android, in the one survey stack. `FinishSheetRoute` feeds `useFinishSheet` (`mobile/src/screens/finish-sheet/`), which flushes the draft, stores a changed choice through `setDraftVisibility` (queue only, no network, nothing stored before the confirm) and then calls `submitSurvey`, the single caller of it; the screen is `FinishSheet` with the `VisibilityPicker` radio group (`mobile/src/ui/`, `RadioCard` shared with `CasPicker`). Strings are `fr.surveyFinish` (`mobile/src/i18n/fr/survey-finish.ts`): "Partagé avec l'association" and "Privé", never "public", mapped from the wire value only by `mobile/src/app/visibility-display.ts`. A new draft is stored shared (`public`); the choice is frozen after submit (the storage guard answers `frozen`), and the summary header of a finished survey shows a read-only visibility line (`resolveVisibilityLine`, none on a draft). `submitSurvey` resolves a `FinishOutcome` (`submitted`, `not_submitted`, `busy`). The SQLite schema is unchanged (still version 5)
- Dendromicrohabitat guide (Phase 32, D-04, D-05): `surveyDmhGuide` (`DmhGuideRoute` in `mobile/src/navigation/routes/`, screen `DmhGuideScreen` in `mobile/src/screens/dmh-guide/`), a form sheet on iOS (detents 0.65 and 1, `dmhGuideScreenOptions`) and a modal on Android, registered in the survey stack only. One sheet with three internal views (catalogue with search, group page, sources and licence), never a sheet over a sheet. The param `{ group }` opens that group's page; none or an unknown code opens the catalogue (the route checks it against `DMH_GROUP_CODES`). The route reads only `ibpMethodVersion` from the form context: groups 6, 12 and 15 show their version 3.0 wording on a version 3.0 survey. It is opened from the F list (each row's info glyph, and the "Guide des dendromicrohabitats" entry) through `FactorPager` and `FactorDetailRoute`
- Export choice (Phase 33): the summary header's "Partager" navigates to `surveyExportChoice { surveyId }`, next to `surveyFinish` (same presentation: a native form sheet on iOS, a modal on Android). The sheet shows two radio cards, the complete PDF and the one-page summary (disabled with a sentence on a draft), and on confirm goes back to `surveyDetail` with `exportRequest { mode, nonce }`. The sheet has a close cross ("Fermer", on both platforms) beside its title and one button "Exporter le PDF", no "Annuler"; on iOS it is fitted to its content (`sheetAllowedDetents: "fitToContents"`, the scroll view bounded by a `maxHeight` so it scrolls at a large text size). Its strings are `fr.surveyExportChoice` (`mobile/src/i18n/fr/survey-export-choice.ts`); `fr.surveyExport` holds the printed texts
- Tab bar rule (D-08): on iOS the native bar (`react-native-bottom-tabs`) is always used in Release builds; the JS bar (`@react-navigation/bottom-tabs`) is used on Android and in Expo Go. `EXPO_PUBLIC_ENABLE_NATIVE_TABS=false` is only honoured in development. Both libraries stay. Tab-bar hiding (e.g. on parcel selection) goes through `shouldHideTabBar` in `navigation/tab-bar.ts` for both trees
- Explorer map layers (Phase 28): `mobile/src/map/layers.ts` is the single catalogue (five bases in the swipe cycle, the Types de forêt overlay, templates, zoom caps, weights); nothing else switches on `"map" | "satellite"` by hand. The globe in the top-right capsule enters the swipe mode (the map recedes into a window between a carousel above and a hint and notices zone below, bare basemaps only; a tap on the map leaves). A release in the middle third opens the single comparison mode: free map, centre line, slim exit-only grabber (the outer fifths quit), side tags with chevrons that step one side. The layers state is in `useMapLayersState` / `map-layers-state.ts`, the pure rules in `map/swipe-machine.ts` and `map/wipe-geometry.ts`. Stacked maps are never shown before they are rendered (`useStackedReady`, `useCoverRelease`). Offline: one native pack per layer in a fixed order (`map` with the cadastre first, the 1950 photographs last), extras best effort, 45 s stall watchdog, Photos 1950 capped at tile zoom 17; on Android the packs are created from `GET /v1/map-styles/{name}.json`. Record: `docs/technical/map-layers-and-licences-v1.md`

- All user-facing text comes from the typed French catalogue `fr` (`mobile/src/i18n/fr/`, one module per screen or area)

At most 12 KiB of data per drawing and 120 KiB for the module, enforced by the gate `mobile/src/__checks__/dmh-drawings.test.ts`; no paper tile and no colour in the data

**HTTP client** (`mobile/src/api/client.ts`):
- Thin wrapper over `fetch` with Bearer token injection, timeout handling, and typed `ApiError`
- Default timeout: 15 s (overridable per-request or via `EXPO_PUBLIC_API_TIMEOUT_MS`)
- Endpoints defined in `mobile/src/api/ibp-api.ts`
- Phase 30: `apiRequest` adds the client marker header `X-Cortege-Features: survey_route` (`CLIENT_FEATURES_HEADER` of the package) to every request; a header the caller sets under the same name wins. The API applies the mandatory route (`route_required`) only to requests that carry it, so older builds keep working. Deploy the API before installing an app build that sends it

**PDF export** (phase 25.1, rebuilt in phase 33; `mobile/src/app/survey-pdf/`):

The PDF is always light, whatever the system appearance

**Database access**: raw SQL via `pg` library through `DatabaseService`. No ORM. Migrations live in `api/migrations/` and run via `api/scripts/migrate.js`.

**Request lifecycle**:
1. `AuthGuard` validates JWT against Auth0 JWKS (RS256)
2. On first login, `UsersService` auto-provisions a DB user from Auth0 `/userinfo`
3. `@CurrentUser()` decorator injects the authenticated user into controllers
4. Controllers delegate to services; services own business logic and DB queries

**IBP validation**: the rules live once, in `@cortege/ibp-domain` (`packages/ibp-domain/`). Both sides delegate to it through thin adapters with no rule code: `IbpRulesService` (`api/src/surveys/ibp-rules.service.ts`) server-side, `mobile/src/app/ibp-scoring.ts` on mobile for immediate client feedback. Never re-implement a rule, allowed score set or factor-key list in `api` or `mobile`.
- Surveys carry `ibp_method_version` (`null` = v3.0; new surveys default to v3.2), and for v3.2 `ibp_cas` (1–4) and `ibp_cas3_scale`; v3.0 surveys carry `region_version` + `vegetation_stage` instead. Always write `ibp_cas`, never a bare "cas": CAS already means compare-and-swap in this codebase
- API: migration `016_ibp_method_version.sql` (nullable columns, CHECK constraints). Mobile: the fields live in the local `payload_json`, no SQLite migration
- `ibp_method_version`, `ibp_cas` and `ibp_cas3_scale` are read-only after submit
- Survey visibility (Phase 29): `PUBLIC_SURVEY_PREDICATE` (`api/src/surveys/public-map.queries.ts`) is the only definition of "another member may read this survey": submitted, live, `visibility = 'public'`, which means shared with the association (never the open internet; the UI never says "public"). Map items, parcel statuses, community list, detail and attachments, community search and parcel search all use it, and nothing may re-derive it by hand. `submittedVisibleToCallerSql` is its caller-aware sibling, used only by the parcel history (the caller's own surveys plus the shared ones). The next version number counts private surveys (D-11: only the number leaks, never content). Visibility is chosen before submit and read-only after it on every channel (422 `submitted_read_only_fields` on PATCH and `visibility_update`, 409 `survey_submitted_read_only` and `sync_version_conflict` on upserts). `POST /v1/reports` answers 404 for a survey the reporter may not read, like an unknown id. `api/test/survey-read-paths.spec.ts` fails on an unclassified route or an unguarded query on `surveys`. Contract: `docs/technical/api-contract-v1.md`
- Since phase 27 a survey also carries `survey_note` (at most 1000 characters) and `weather` (migration `023_survey_note_weather.sql`, nullable columns), and the observer's per-factor doubt and note live in the `factors.annotations` container (keys A to J, `{ doubt?: true, note?: string }`, note at most 300 characters), never inside a factor entry. No scorer reads the container: the parity cases `MAT-ANN-*` prove the same survey with and without a doubt scores and validates identically. The package owns the limits and helpers in `packages/ibp-domain/src/conditions.ts`. All three are read-only after submit; the notes of retained submitted surveys survive account deletion (D-24)
- Since phase 30 a survey also carries `survey_route` (migration `025_survey_route.sql`, nullable JSONB, checks `chk_surveys_survey_route_object` and `chk_surveys_survey_route_size`, at most 4096 bytes): the route used, closed codes and numbers only. Its shape, bounds, canonical form and validator (`validateSurveyRoute`, `readSurveyRoute`) and the choice rules (`recommendRoute`, `routeQuestionsFor`, the decision table `ROUTE_RULE_CASES`) live only in the package, `packages/ibp-domain/src/route/` (`record.ts`, `guide.ts`, `cases.ts`) plus `factor-details.ts` for the uncapped detail keys `strata_cover` (B), `dmh_counts` and `surface_ha` (F). Never re-implement a route rule, threshold or code in `api` or `mobile`. **The score never depends on the route**, and no scorer reads it or the detail keys (parity cases `MAT-B-UNC-*` and `MAT-F-UNC-*`). The route is mandatory for a new survey of the current app and never deleted (absent or `null` keeps the stored one), read-only after submit, compared by value. The API refuses a create or a submit without it (`422 route_required`) only for a request carrying the marker header; the surveys submitted before the phase keep `null` ("Parcours : non renseigné"). Rules: `docs/specs/route-choice-rules-v1.md`; contract: `docs/technical/api-contract-v1.md`, "Survey route (phase 30)"; deploy the API first
- Package resolution: Metro, Jest (`moduleNameMapper`) and `tsc` read the package's `src`; Node at runtime reads its `dist` (`npm run build:domain`, built in the API Docker image). Do not add a `prepare` script to the package

### IBP domain

The IBP score is composed of **10 factors (A–J)**, each representing a biodiversity dimension:

| Factor | Focus area |
|--------|-----------|
| A | Native genus count |
| B | Vegetation strata and native cover |
| C/D | Deadwood (standing/fallen) |
| E | Old/veteran trees |
| F | Tree density |
| G | Open flowering plant cover |
| H | Connectivity class |
| I | Ground cover types |
| J | Water/wetland types |

Subscores: stand and management A–G (/35) and context H–J (/15); totals are shown out of 50. Band colours come from the package (`standBand`, `contextBand`, `totalBand`); the /50 total bands (10/20/30/40) are an app convention, the CNPF chart only bands /35 and /15. The band cut points are exported as `STAND_BAND_CUT_OFFS` and `CONTEXT_BAND_CUT_OFFS` (read by `standBand`, `contextBand` and the PDF plane).

Since phase 25.1 the factor payload also stores `B.strata`, `F.dmh_groups`, `H.evidence`, `I.types` and `J.types` (catalogue codes, the CNPF typology per method for I and J, written only with their scored key and never scored; `mobile/src/app/factor-selections.ts`).

Since phase 32 the F entry is a sectioned group list. `DmhGroupList` and `DmhGroupRow` (`mobile/src/screens/factor-detail/`) replace F's chips and counter rows: seven sections by form, ordered once when the page mounts (`orderDmhRows` in `mobile/src/app/dmh-guide/order.ts`: ticked or counted groups first, then `DMH_LIST_ORDER`; a section starts open when it holds a ticked or counted group, or when nothing is ticked), never while tapping. In the counted-in-full mode only, an unticked row shows a "+" (`bumpDmhGroup` of `useSurveyForm`: ticks and counts 1 in one call) and a ticked row a `DmhCounterStepper` (`mobile/src/ui/`; `DMH_STEPPER_SIZE` = 48, validated for O-32-1 on 2026-10-27, shared by the stepper and the row's "+"). "-" down to 0 keeps the tick, and a counted group cannot be unticked until its count is 0 (a caption says so). `DmhCountFields` keeps only F's surface. The stored payload is unchanged (`dmh_groups` in option order, `dmh_counts`, `trees_per_ha`), pinned by `dmh-entry-cost.test.tsx` and the `useSurveyForm` test against the recorded old flow (`OLD_FLOW_F_PAYLOAD` in `dmh-entry-scenarios.ts`). The guide computes no density, cap or score.

Factor validation matrix: `docs/technical/ibp-validation-matrix-v2.md` (executable form: `IBP_PARITY_CASES`; v1 is the pre-01.8 baseline)
Method version: the app implements IBP FR v3.2, with IBP Fr v3.0 available per survey (ADR-003, `docs/technical/adr-003-ibp-method-version-v1.md`; comparison: `docs/technical/ibp-version-comparison-v3.0-v3.2.md`).

| `METEOFRANCE_OBS_URL`, `WEATHER_TIMEOUT_MS`, `WEATHER_MAX_STATION_DISTANCE_KM`, `WEATHER_SYNOP_MAX_DISTANCE_KM`, `WEATHER_TIME_TOLERANCE_MINUTES` | Optional weather settings: observation API base URL, provider timeout, the cap on the distance to the nearest hourly station (`WEATHER_MAX_STATION_DISTANCE_KM`, default 30 km, measured by the spike, D-19), the cap on the distance to the nearest SYNOP station for sky and rain over 24 h (`WEATHER_SYNOP_MAX_DISTANCE_KM`, default 50 km, D-29) and the tolerance between the survey time and a reading (default 90 minutes) |
| `GEOCODING_IGN_SEARCH_URL` | Place search of the global search (default `https://data.geopf.fr/geocodage/search`); switched by `CADASTRE_PROVIDER` |
| `DEBUG_DATA_RESET_ENABLED` | Gates `/v1/debug/reset-ibp-data` and `/v1/debug/reset-user-data` (dev-only) |
| `TRUST_PROXY` | Express trust-proxy value (default `loopback,uniquelocal`); trusts Caddy's `X-Forwarded-For` for per-client rate limits without trusting public peers |
| `CORS_ORIGIN` | Required in production: `none` (no browser origin) or a comma-separated origin list; startup refuses otherwise |

The API sends no email: the SMTP settings and `EmailService` were removed (phase 01.9). Do not re-add them; `infra/vps/check-env.sh` reports leftover `SMTP_*` lines as obsolete.

## CI/CD

### GitHub Actions

**`ci.yml`** — runs on every push and PR to `main`, plus manual `workflow_dispatch`. Jobs:
1. `changes` — detects which paths changed, to gate the path-filtered jobs below
2. `check` — lint (`npm run lint`), format check (`npm run format:check`), typecheck (`npm run typecheck`), `actionlint` over `.github/workflows/*.yml`
3. `unit-api` — API unit tests, including the `ibp-domain` package (`npm --workspace @cortege/ibp-domain run test:coverage`)
4. `unit-mobile` — mobile unit tests
5. `e2e` and `e2e-minio` — API E2E against a test PostgreSQL service, in local-storage and MinIO-storage modes
6. `mobile-build` — `expo-doctor`, `expo export` (bundle checks)
7. `native-android` and `native-ios` — unsigned native builds (`gradlew assembleRelease` / Release-simulator `xcodebuild` on `macos-26`), each after `expo prebuild --clean`; path-filtered to `mobile/package.json`, `mobile/app.json`, `mobile/plugins/**`, `mobile/assets/**`, the Babel/Metro configs, `packages/**`, `package.json`, `package-lock.json`, `ci.yml` (JS/TS-only changes under `mobile/src/` skip them; `mobile-build` still bundles them), or run on `workflow_dispatch`. See `mobile/README-native.md`
8. `audit` — `npm run audit:check` (`scripts/audit-check.mjs`): fails on any high or critical advisory except those listed with a reason in `scripts/audit-allowlist.json` (advisories with no patched release upstream), and on a listed entry that no longer matches, so the list shrinks by itself
9. `image-check` — Docker image build when `api/**` or `packages/**` changed; its smoke tests check the image runs as non-root, holds no mobile dependency, and loads the built `ibp-domain` package
10. `ci-ok` — aggregate gate; both native jobs are in its required set (success or skipped), and `image-check` waits on it
11. `build` — pushes the image on `main` (see Deployment below). It runs on `always()` gated by `ci-ok` itself, because a job skipped further up the chain (the native builds, when only the API changed) would otherwise skip it too and the image would never be published (found 2026-10-06 after PR #235)

A separate `codeql.yml` workflow runs CodeQL analysis.

**Deployment** — pull-based, no workflow:

- `ci.yml` publishes `ghcr.io/florianlepont/cortege:latest` (linux/amd64) on `main` pushes touching `api/**` or `packages/**`
- A systemd timer on the VPS polls the registry every 5 minutes and restarts the stack when the digest changes
- `infra/vps/update-stack.sh` runs the new image's configuration check before restarting; on failure the previous API keeps serving
- The host's Caddy serves `cortege.algernon.ovh` and `cortege-files.algernon.ovh`; the stack publishes on the loopback only
- Attachment URLs are presigned, so `OBJECT_STORAGE_ENDPOINT` must be the public name clients call
- Runtime secrets live in `/home/ubuntu/cortege.env` on the VPS
- Setup and operations: `infra/vps/README.md`

### Branch workflow

- Feature work → PR → `main`
- CI must pass before merge
- No force-pushes to `main`
