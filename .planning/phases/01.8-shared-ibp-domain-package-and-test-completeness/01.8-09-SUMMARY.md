# Phase 01.8 Plan 09: Method version and cas persisted per survey Summary

Every survey now stores its IBP method version (NULL = v3.0) and, for v3.2, its `ibp_cas` and `ibp_cas3_scale`. The API validates and scores each write under the survey's effective version and keeps these fields fixed after submit. An installed app replaying a legacy submitted survey still gets `synced`, and the stored scores are left as they were.

## What changed

- **Migration 016** (`api/migrations/016_ibp_method_version.sql`)
  - `ADD COLUMN IF NOT EXISTS` adds three nullable columns with no default.
  - Two CHECK constraints: `chk_surveys_ibp_method_version`, which allows the two known tags, and `chk_surveys_ibp_cas`, which allows 1-4.
    - Each is added only when absent, `NOT VALID`, then `VALIDATE`d.
  - There is no backfill. The header follows the 015 style: runner lock and BEGIN/COMMIT, NULL means v3.0, and the old API keeps serving.
- **DTOs.** `@IsOptional() @IsIn(IBP_METHOD_VERSIONS)`, `@IsIn(IBP_CAS_VALUES)` and `@IsBoolean()` are on both the upsert and patch DTOs. REST rejects unknown values with a 400. `/v1/sync` keeps valid values and turns invalid ones into `invalid_sync_operation`, listing the field names.
- **`resolveSurveyMethodColumns(body, existing)`** implements RESEARCH §4.2 rules 1-2:
  - version = the body's tag, else the stored tag;
  - v3.2 → region and stage are NULL, and cas and flag come from the body, else the stored row;
  - v3.0 → cas and flag are NULL, and region and stage come from the body, else the stored row;
  - an untagged row is never stamped.
- **Service**
  - `prepareUpsert` scores the body alone before any statement.
  - `prepareForRow` re-scores it under the stored row's context only when the resolved columns differ. This applies to the fast path, the locked path and the missed-write settle.
  - The fast path's statement count is unchanged: `sync-query-budget` is green.
  - The fast create/update CTEs (`$24..$26`), the locked insert/update and PATCH write the columns explicitly.
  - Submit passes the stored method fields.
  - The detail projection returns the three fields.
- **Read-only rule.**
  - `getChangedSubmittedReadOnlyFields` compares `ibp_method_version` with `isSameMethodVersion`, and `ibp_cas` / `ibp_cas3_scale` under v3.2 only.
  - Region and stage are compared only under v3.0.
  - `getSubmittedReadOnlyFields` (PATCH key presence) lists the three fields.
- **Sync service.** The feed SELECT includes the three columns. The dead `IbpRulesService` injection is removed, and the constructor now takes 3 parameters.

## Deviations from Plan

1. **[Rule 1] A null method field counts as absent.** The plan's formula is `body.ibp_method_version !== undefined ? body : existing`, which lets an explicit null switch a stored v3.2 draft back to v3.0 (NULL). The read-only rule already treats a null body field as unchanged, so null is now absent on write too (`??`).
   - An old or new app sending null can then never silently change the method.
   - Switching back to v3.0 needs the explicit v3.0 tag.
   - Unit and E2E tests cover both.
2. **[Rule 2] The read-only comparison is normalised beyond the version.** The cas fields are compared only when the effective method is v3.2, region and stage only under v3.0, and a missing cas-3 flag equals false. Without this, a replay sending a field that the write normaliser clears would be a false 409 conflict (the Pattern 3 rationale).
3. **PATCH after submit is 422, not 409.** PATCH already rejects any read-only key with 422 `submitted_read_only_fields`, and the method fields are added to that key list. The plan's "PATCH/replay → 409" holds for replays: POST and /v1/sync give 409 `survey_submitted_read_only`. The E2E asserts both.
4. **[Rule 2] PATCH re-scores when the method context changes.** A PATCH that changes the version, cas or region without sending factors now re-scores the stored factors, so `scores` and `factor_results` always match the stored method.
5. **Validation context includes the stored region/stage.** Before, upsert validation used the body's region/stage only, while the write used body else stored. It now uses the same resolved columns as the write (rule 4, generalised). Only bodies that omit region/stage on a row that has them are affected.
6. **Migration lock comment.** The runner applies each file in one transaction, so `ADD COLUMN`'s ACCESS EXCLUSIVE lock is held until COMMIT, and `NOT VALID` + `VALIDATE` gives no lock benefit here. It is kept as the plan asks (idempotent guards, and a future rerun can split VALIDATE out), and the header says so honestly. The table holds test data only (D-04).
7. **Environment.** The sandbox refused to `source` the scratchpad `e2e-env.sh`, so the same variables were exported inline (POSTGRES_DB=ibp_p18_09_test, ACCESS_TOKEN_SECRET unset).
8. **Out of scope and left alone.**
   - Public map items and parcel statuses (RESEARCH §4.2 rule 6, `ibp_method_version` / `latest_ibp_method_version`) are not in this plan's files; they are left to the public-map plan.
   - The `./src/auth/` coverage row measures above its threshold (88/78/83/89 against 87/78/82/89) because of earlier plans. It was not raised here, because this plan owns only the surveys row.
