## Summary

The shared package is straightforward to add, and every toolchain was proven in a throwaway git worktree of this repo (since removed): with `packages/ibp-domain` added to the root `workspaces`, `"@cortege/ibp-domain": "*"` in `api` and `mobile`, and a package.json of `main: dist/index.js`, `types: src/index.ts`, `react-native: src/index.ts`, then (a) `tsc -p api/tsconfig.build.json` type-checks against the package source and still emits `api/dist/main.js` in place; (b) `npx expo export --platform android` bundles the package **from source with no `dist` present** (the Hermes bundle contains the probe constant); (c) Jest in both workspaces resolves it through a `moduleNameMapper` to `src/index.ts`; (d) the proposed Dockerfile builds, the runtime image has the `node_modules/@cortege/ibp-domain` link plus `dist`, no `expo`/`react-native`, and `require()` works. `npm install --offline` changed only 14 lockfile lines. Two traps were found empirically: **a `prepare` script in a workspace package runs even under `npm ci --ignore-scripts`** (npm 10.9.7), which would break the Docker runtime stage (no TypeScript there); and **`workspace:*` is rejected by npm** (`EUNSUPPORTEDPROTOCOL`), so the dependency must be `"*"`.

The rule inventory is small and fully duplicated: `api/src/surveys/ibp-rules.service.ts` (510 lines) and `mobile/src/app/ibp-scoring.ts` (352 lines) are line-for-line twins except for the `factor_f_group_capped` warning (API only), the submit-readiness function (mobile only) and the consistency warnings (API only). Factor-key lists are repeated in six places, `FactorCanonical` in two, and the sync contract types live in `api/src/surveys/surveys.types.ts` and `mobile/src/storage/types.ts`. The v3.2 engine needs only three new inputs: the method version, the cas (plus one "cas-3 scale" flag the D-08 cas-only model cannot express for cas 2 and the special habitats), and the Factor A native-cover estimate. Everything else in the 20 field-definition rows is help text.

D-05 is safe: upsert validation never compares recomputed scores with stored ones (`scores` is excluded from the read-only comparison, `surveys-normalize.utils.ts` l. 87–94), and a replay of a submitted survey only rewrites `visibility`/`sync_version` (`surveys.service.ts` l. 387–427). The only replay that the fixed v3.0 rules would reject is a stored **direct** `G = 1`/`H = 1`, which the mobile form cannot produce (G is computed from a percentage, H is restricted to 0/2/5 at `useSurveyForm.ts` l. 185 and 453) — but 31 E2E fixture sites across 5 specs use exactly that shape and must move to 2. Three CONTEXT decisions need correcting (see "CONTEXT decisions to revisit"): the SQLite migration 3 is unnecessary, the CNPF bands cannot colour a /50 total literally (they are per axis, /35 and /15), and a cas value alone cannot drive the A/G scale for cas 2.

**Primary recommendation:** 12 plans in 6 waves: toolchain wiring first (one plan owns every package.json, the lockfile, the Dockerfile and `ci.yml`), the RS256 and E2E-split test work in parallel with it, then the pure package, then API and mobile adoption in parallel, then UI and public-map work, docs, and a phase gate with the owner's 6-step iPhone check.

One boolean covers both (assumption A6 of the comparison: the special-habitat rule applies whatever the cas). ADR-003 CH-4 proposed three fields (macro cas, infertile flag, habitat flag); the D-08 "observer ticks cas 1–4, as on the p. 20 sheet" plus one override flag is equivalent for the engine and closer to the paper sheet.

### 4.2 Recommended design (least disruptive)

**API migration `016_ibp_method_version.sql`** (additive, one transaction under `migrate.js`'s lock):

```sql
ALTER TABLE surveys
  ADD COLUMN IF NOT EXISTS ibp_method_version TEXT,
  ADD COLUMN IF NOT EXISTS ibp_cas SMALLINT,
  ADD COLUMN IF NOT EXISTS ibp_cas3_scale BOOLEAN;
ALTER TABLE surveys ADD CONSTRAINT chk_surveys_ibp_method_version
  CHECK (ibp_method_version IS NULL OR ibp_method_version IN
         ('cnpf_ibp_fr_v3_0_2023-03-23', 'cnpf_ibp_fr_v3_2_2026-02-02'));
ALTER TABLE surveys ADD CONSTRAINT chk_surveys_ibp_cas
  CHECK (ibp_cas IS NULL OR ibp_cas IN (1, 2, 3, 4));
```
Nullable columns without default are metadata-only in PostgreSQL 16; the CHECKs scan the (small) table once [ASSUMED: size]. All existing rows stay NULL = v3.0 (D-02). The previous API keeps serving during `update-stack.sh`: its explicit column lists ignore the new columns, so the migration is safe to run before the restart.

**Server rules (in `SurveysService`):**
1. Effective version = `resolveMethodVersion(body.ibp_method_version ?? existing?.ibp_method_version)`; null → v3.0.
2. Normalise on write: v3.2 rows store `region_version = NULL, vegetation_stage = NULL`; v3.0 rows store `ibp_cas = NULL, ibp_cas3_scale = NULL` (D-08 "v3.2 surveys carry no region/stage"; also needed because the `body.x ?? existing.x` pattern can never clear a field).
3. Read-only list for submitted surveys gains `ibp_method_version`, `ibp_cas`, `ibp_cas3_scale`, compared **normalised** (`resolveMethodVersion(null) === resolveMethodVersion("cnpf_ibp_fr_v3_0…")`), so a client that sends the explicit v3.0 tag for a legacy NULL row is an identical replay, not a 409.
4. Validation must use the effective version, not only the body: `prepareUpsert` (l. 209–251) runs before the row is read, so an old app editing a v3.2 draft without sending the version would be scored under v3.0. Either move the rule evaluation after the read (pure CPU, no extra statement, keeps the 01.x fast-path statement count), or re-evaluate when `body` has no version and the row has one. Edge case (needs a second device on an old build), but cheap to get right.
5. DTOs: `@IsOptional() @IsIn([V3_0, V3_2]) ibp_method_version`, `@IsOptional() @IsIn([1,2,3,4]) ibp_cas`, `@IsOptional() @IsBoolean() ibp_cas3_scale` on upsert and patch DTOs; `region_version` stays optional.
6. Responses: detail, sync feed, public map items (`ibp_method_version`), parcel statuses (`latest_ibp_method_version` from the LATERAL row) — all additive.

**Public map (D-10):** keep the `region` filter matching `region_version` exactly (it then only matches v3.0 surveys; document it, CH-9). Add `ibp_method_version` to items; mobile cards show the version and, for v3.2, "Cas N" instead of the raw `region_code` ("unknown" today for any null region). The sector average (`useNearbyParcels.ts` l. 87–93) mixes versions: ADR-003 says readers "must either show the method version or never mix versions in one figure"; recommend showing a "méthodes v3.0 et v3.2 mêlées" meta line when `latest_ibp_method_version` differs across the averaged parcels (both are /50 with the same aggregation).

**Mobile storage:** the version and cas live in `payload_json` and the queue payload (both schemaless JSON). No SQLite column is needed: nothing lists or filters by version, and the completion precompute can read them from the payload at write time. **Recommend skipping the D-10 "migration 3"** (see "CONTEXT decisions to revisit"). Required code changes: `SurveyQueuePayload`, `DraftInput`, `UpdateDraftInput`, `RemoteSurvey` gain the three fields (region/stage become optional); `createLocalDraft`/`updateLocalDraft` write them (the update spreads `basePayload` first, l. 361–375, so an untouched field survives, but `region_version: input.region_version` must not re-add region to a v3.2 payload); `buildSurveyPayloadFromRemote` (`sync.ts` l. 437–451) must copy them or every pulled v3.2 survey silently becomes v3.0 on the phone; `computePayloadCompletion` (`storage/utils.ts` l. 72–100) counts "version + cas" for v3.2 in place of "region + stage" (keeps 14 slots, so existing stored values stay correct and need no backfill).

**Legacy rows on the phone:** never stamp a version onto legacy payloads (keep `undefined`/`null`), so replays stay byte-identical to what the server stored.

### 4.3 D-05 replay safety — confirmed safe (with one fixture consequence)

Evidence [VERIFIED: code read]:
1. `prepareUpsert` (`surveys.service.ts` l. 222–233) rejects only when `validateDraft(...).ok` is false, i.e. a **blocking** issue: `factor_invalid_raw` (an object that no scorer can read) or `factor_invalid_score` (outside the allowed set). It never compares recomputed scores to stored ones.
2. `scores` is excluded from the submitted read-only comparison (`surveys-normalize.utils.ts` l. 87–94, doc: "`scores` is excluded: it is recomputed server-side and must never block a resync"), and a submitted replay writes only `visibility`, `sync_version`, `updated_at` (l. 399–427). Stored `factor_results`/`scores` are never rewritten.
3. The mobile app shows server scores for submitted surveys (`SurveyDetailScreen.tsx` l. 126: local recompute only when `status !== "submitted"`) and does not persist `factor_results` from sync results (grep: only `SurveyDetailScreen.tsx` l. 111 reads them).
4. Fixed v3.0 rules on every shape the app ever produced: A `{native_genus_count}` → scored (cap from B's legacy cover); B `{strata_count, covered_autochthonous_percent}` → scored (cover ignored); C–F, I, J unchanged; G `{open_flowering_percent}` → 0/2/5 by construction; H `{class_score ∈ {0,2,5}}` (form-enforced, `useSurveyForm.ts` l. 185, 453). None becomes blocking.
5. The only newly-blocking stored shapes are **direct** `G: 1`, `H: 1` or `H: {class_score: 1}` — reachable only through direct API calls. In the repo they exist in **31 E2E fixture sites in 5 specs** (`surveys-idempotency` ×17, `epic-e-search-reports` ×6, `surveys-transactions` ×2, `surveys-same-version` ×1 line, `sync-installed-app-compat` ×2) and 3 unit sites (`ibp-rules.spec.ts` l. 195, 223, 246). They must move to 2 (and expected totals +1 per factor). In production, run ADR-003's read-only `g_h_score_1` count during the phase gate; D-04 lets the owner delete any hit.

Therefore **no frozen legacy path is needed**. The behavioural change for legacy data is limited to: a replayed legacy survey's *response* `factor_results`/`warnings` may differ from what is stored (not persisted by the phone), and a legacy **draft** reopened on the new app is re-scored with the fixed v3.0 rules (B no longer capped, A capped from B's cover) — acceptable under D-04/D-05 and not a version change.

### 4.4 Installed (old) apps after the deploy

- Old app, legacy survey: payload has no version → v3.0 → accepted (above).
- Old app, new survey: v3.0 (untagged); scored server-side with the fixed v3.0 rules while the old phone previews with its old engine (B capped) → the phone's preview can differ from the stored score until it pulls. Test users only (D-04).
- Old app, pulled v3.2 survey from another device: the old `buildSurveyPayloadFromRemote` drops the version and cas; an edit replays it untagged → rule 4.2(4) keeps it v3.2 (effective version from the row). Without that rule it would be scored v3.0.
- **Deployment order matters:** a new app talking to the *old* API sends v3.2 payloads whose B has no cover → the old engine returns `factor_invalid_raw` → 422 → fatal (01.5 D-05 blocks immediately). The API image must be deployed (merge → `ci.yml` build → VPS timer, ≤ 5 min) before the owner installs the new app build. Put that order in the gate plan.

### 6.1 RS256 path of `AuthGuard` against a local JWKS (criterion 4, D-12)

How it works today [VERIFIED]: the guard builds one `JwksClient` per Auth0 domain with `jwksUri: https://${domain}/.well-known/jwks.json`, `cache: true`, `cacheMaxAge: 10 min`, `rateLimit: true` (`auth.guard.ts` l. 72–84); `verifyToken` decodes the header, requires `kid`, fetches the key, then `jwt.verify` with `audience`, both issuers and `algorithms: ["RS256"]` (l. 131–156); `getSigningKey` tries each client (l. 158–174). In `NODE_ENV=test` the guard takes the HS256 path instead (l. 97–101), so the RS256 test must build the guard with a non-test config (the existing `productionConfigService()` helper, `auth.guard.spec.ts` l. 21–26). The E2E Jest config maps `jwks-rsa` to a stub (`api/jest.config.js` l. 11, `test/__mocks__/jwks-rsa.js`); the **unit** config does not, so the real `jwks-rsa` 4.0.1 is available in `api/test/*.spec.ts`. jwks-rsa fetches with Node's `http`/`https` according to the URI scheme (`node_modules/jwks-rsa/src/wrappers/request.js`).

Approach (no network, no new dependency):
1. `generateKeyPairSync("rsa", {modulusLength: 2048})` twice (signing key + an unrelated key); build the JWK with `publicKey.export({format: "jwk"})` plus `kid`, `alg: "RS256"`, `use: "sig"`.
2. Start `http.createServer` on `127.0.0.1:0` serving `{"keys":[jwk]}` at `/.well-known/jwks.json`; count requests (proves the JWKS was actually fetched).
3. Point the guard at it with a small seam: extract the URI builder into a protected method (`protected jwksUriFor(domain) { return \`https://${domain}/.well-known/jwks.json\` }`) and use a test subclass that returns `http://127.0.0.1:${port}/.well-known/jwks.json`. The base constructor calls the overridden method (prototype dispatch works during `super()`), so the real client options (cache, rateLimit) are exercised. Alternative with no production change: replace the private `jwksClients` array with a `new JwksClient({jwksUri: local, cache: true, rateLimit: true})` via a typed cast, as the existing spec already does for other internals (l. 221–225, 283–304).
4. DB mock: `query` returns the existing user row for the `auth0_sub` lookup (`getOrProvisionUser` l. 183–191), so `fetchUserInfo` is never called.
5. Cases through `canActivate` (full path): valid token → `true`, `request.user` set; expired (`expiresIn: -10` or `exp` in the past) → `UnauthorizedException`, log contains `TokenExpiredError`; wrong audience → 401, `JsonWebTokenError: jwt audience invalid`; unknown `kid` → 401 via `SigningKeyNotFoundError`, and the server saw a (re)fetch; plus two cheap hardening cases: wrong issuer → 401, and an HS256 token signed with the RSA public PEM (algorithm confusion) → 401. Close the server in `afterAll`.
6. File: `api/test/auth.guard.rs256.spec.ts` (unit config picks it up: `testMatch **/*.spec.ts`). `./src/auth/` coverage floor (87/78/82/89) can only rise.

### Pattern 1: Adapter over the package, identical names kept
**What:** `IbpRulesService` and `mobile/src/app/ibp-scoring.ts` keep their exported names and become thin adapters; callers change only their arguments (context object).
**When:** everywhere a rule is evaluated.
```ts
// api/src/surveys/ibp-rules.service.ts (sketch)
@Injectable()
export class IbpRulesService {
  validateDraft(input: IbpEvaluationInput): IbpValidationResult {
    return evaluateIbp(input, "draft")
  }
  validateSubmit(input: IbpEvaluationInput): IbpValidationResult {
    return evaluateIbp(input, "submit")
  }
}
```

### Pattern 2: One parity fixture, three runners
**What:** `IBP_PARITY_CASES` (typed data) is asserted in `packages/ibp-domain/src/parity.test.ts` against `evaluateIbp`, in `api/test/ibp-parity.spec.ts` through `new IbpRulesService()`, and in `mobile/src/app/ibp-parity.test.ts` through the mobile adapter (retained scores, totals, readiness). A case lists `method`, `mode`, context, `factors`, and expectations (per-factor score or `null`, totals, issue codes, incomplete factors).

### Pattern 3: Version-normalised comparisons
Any equality on the method version (read-only check, same-version classification, UI "is v3.0") goes through `resolveMethodVersion`, never raw string equality, because legacy rows are NULL.

### Anti-Patterns to Avoid
- **A `prepare` script in the package** (runs under `--ignore-scripts`, breaks Docker).
- **Stamping `v3.0` on legacy payloads** in a mobile migration (turns identical replays into 409 conflicts if the server compares raw values).
- **Adding a field to `SurveyUpsertBody` but not to the DTO class** (silently stripped on `/v1/sync`).
- **Calling the v3.2 input `cas`** anywhere: the codebase already uses "CAS" for compare-and-swap (`cas_token`, `surveys.repository.ts` l. 142; `surveys-upsert-cas.e2e-spec.ts`). Always `ibp_cas`.
- **Re-scoring submitted surveys** (ADR-003: never recompute; the phone already shows server scores for them).
- **Averaging or colouring a /50 total with the /35 stand bands** without saying so.

## Common Pitfalls

### Pitfall 1: `prepare` runs despite `--ignore-scripts`
**What goes wrong:** the Docker runtime stage (`npm ci --omit=dev --ignore-scripts`, no TypeScript, no source) fails.
**Why:** npm 10.9.7 runs a linked workspace's `prepare` even with `--ignore-scripts` [VERIFIED].
**How to avoid:** only `build`; call it explicitly (Dockerfile, `build:domain`).
**Warning signs:** `npm error path …/packages/ibp-domain` during `npm ci`.

### Pitfall 2: CI path filters miss `packages/**`
**What goes wrong:** a package-only change merges green, the `build` job is skipped, production keeps old rules; native jobs skipped.
**How to avoid:** add `packages/**` to `shared`, `image` and `native` filters. **Warning:** PR shows `image-check`/`native-*` "skipped" for a package change.

### Pitfall 3: New fields silently stripped on `/v1/sync`
**What goes wrong:** the sync DTO validation uses `whitelist: true, forbidNonWhitelisted: false` (`sync-operation-validation.ts` l. 23–28), so an `ibp_method_version` not declared on `SurveyUpsertDto` disappears and every survey is stored as v3.0.
**How to avoid:** DTO first; E2E asserts the stored column after a `/v1/sync` upsert.

### Pitfall 4: Pull mapping drops the version
`buildSurveyPayloadFromRemote` (`storage/sync.ts` l. 437–451) copies an explicit field list. Add the three fields and a unit test (pull a v3.2 survey, read `payload_json`).

### Pitfall 5: E2E fixtures with direct `G: 1`/`H: 1`
31 sites in 5 E2E specs + 3 in `ibp-rules.spec.ts` become 422/blocking with BUG-2 fixed. Change them in the E2E-split plan (wave 1: 2 is valid under the old rules too, so the suite stays green before and after the rule change) and recompute expected totals.

### Pitfall 6: Coverage ratchet after moving code out
`ibp-rules.service.ts` (510 well-tested lines) leaves `api/src/surveys/` (floor 81/67/79/82) and `ibp-scoring.ts` leaves `mobile/src/app/` (floor 86/73/93/91). Removing well-covered code can drop a directory's percentage below its floor and fail CI. Measure with `node scripts/coverage-by-directory.js api|mobile` before and after; add tests to what remains or record the justified re-baseline in the same plan (the package gets its own high threshold, so total coverage rises). Owner of the threshold files: the API plan for `api/jest.unit.config.js`, the mobile logic plan for `mobile/jest.unit.config.js`.

### Pitfall 7: Old API + new app
Covered in §4.4: deploy the API image before installing the new build.

### Pitfall 8: "cas" naming collision
Existing "CAS" = compare-and-swap (`cas_token`, `surveys-upsert-cas.e2e-spec.ts`). Prefix everything `ibp_cas`; name the new E2E file `surveys-method-version.e2e-spec.ts`, not `*-cas*`.

### Pitfall 9: Catalogue test calls every function leaf
`i18n/catalogue.test.ts` feeds a Proxy to every function in `fr` and checks the output for id patterns. Per-cas help texts should be static maps, and new functions must render sensibly with a string argument.

### Pitfall 10: Metro serves stale code only if pointed at `dist`
With the `react-native` field → `src`, the phone always bundles current rules. If the fallback (dist) were ever used, add a build step to `mobile-build` and both native jobs.

### Pitfall 11: Owner's Release build
`npx expo run:ios --device --configuration Release` bundles through Metro → source (no build step needed with the hybrid shape). Owner still needs `npm install` after pulling (new workspace link).

### Loopback JWKS for the RS256 spec
```ts
// Source: node:crypto KeyObject.export({format:"jwk"}) (Node ≥ 15.9); jwks-rsa 4.0.1 request.js uses http for http: URIs
import { generateKeyPairSync, randomUUID } from "crypto"
import { createServer, Server } from "http"
import { AddressInfo } from "net"
import * as jwt from "jsonwebtoken"

const { privateKey, publicKey } = generateKeyPairSync("rsa", { modulusLength: 2048 })
const kid = `kid-${randomUUID()}`
const jwk = { ...publicKey.export({ format: "jwk" }), kid, alg: "RS256", use: "sig" }
let hits = 0
const server: Server = createServer((req, res) => {
  hits += 1
  if (req.url !== "/.well-known/jwks.json") { res.statusCode = 404; res.end(); return }
  res.setHeader("content-type", "application/json")
  res.end(JSON.stringify({ keys: [jwk] }))
})
await new Promise<void>((resolve) => server.listen(0, "127.0.0.1", resolve))
const port = (server.address() as AddressInfo).port

const sign = (over: jwt.SignOptions = {}, key = privateKey, keyid = kid) =>
  jwt.sign({ sub: "auth0|rs256-user" }, key, {
    algorithm: "RS256", keyid, audience: "aud-1", issuer: "https://tenant.example/",
    expiresIn: "5m", ...over,
  })
```

## Security Domain

### Applicable ASVS Categories
| ASVS Category | Applies | Standard Control |
|---------------|---------|-----------------|
| V2 Authentication | yes (token validation) | `jsonwebtoken` RS256 with pinned `algorithms`, audience and issuer; `jwks-rsa` cache + rate limit — now tested for real (valid, expired, wrong audience, unknown kid, wrong issuer, HS256-with-public-key confusion) |
| V3 Session Management | no | unchanged (Auth0 native SDK) |
| V4 Access Control | yes (unchanged) | ownership checks in `SurveysRepository.findOwned*`; the new fields ride the same owned writes; version immutability after submit enforced server-side |
| V5 Input Validation | yes | `class-validator` `@IsIn`/`@IsBoolean` for `ibp_method_version`, `ibp_cas`, `ibp_cas3_scale`; DB CHECK constraints as a second line; the package treats unknown versions as blocking |
| V6 Cryptography | tests only | Node `crypto.generateKeyPairSync` for test keys; never hand-roll JWT/JWK |

### Known Threat Patterns for this stack
| Pattern | STRIDE | Standard Mitigation |
|---------|--------|---------------------|
| Algorithm confusion (HS256 signed with the RSA public key) | Spoofing | `algorithms: ["RS256"]` pinned (l. 146); add a test |
| JWKS flooding with random `kid`s | DoS | `rateLimit: true` on `JwksClient` (l. 82); unknown-kid test proves the failure path returns 401 |
| Client picks v3.0 to game a score | Tampering | allowed by design (D-02), but the version is recorded, shown and immutable after submit |
| Changing the method version of a submitted survey via replay | Tampering | read-only comparison includes the version (normalised) → 409 |
| Unknown field smuggling on `/v1/sync` | Tampering | whitelist strips unknown fields; the new fields are explicit with `@IsIn` |
