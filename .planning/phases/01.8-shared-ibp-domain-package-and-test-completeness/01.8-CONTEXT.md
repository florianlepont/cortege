<decisions>
## Implementation Decisions

### Owner decisions (2026-09-26)
- **D-01, migrate to IBP FR v3.2** per ADR-003. New surveys default to v3.2.
- **D-02, one method version per survey.**
  - Every survey stores `ibp_method_version`. The observer chooses it when creating a survey: v3.2 by default, v3.0 available, for example to re-survey a parcel under the same method as its earlier survey.
  - The version is fixed once the survey is submitted. The form, help texts, validation and scoring all follow the chosen version.
  - A survey with no version (every survey recorded before this phase) is v3.0.
- **D-03, score out of 50.** The total is shown out of 50, as in the methodology, everywhere a total appears (home sector card, nearby-parcel badge, survey list and detail). Colours follow the CNPF interpretation bands, which are unchanged between versions (GS-2).
- **D-04, production holds only test surveys.** The owner may delete them, and no real field survey exists. So there is no real-data migration risk. The version dispatch (CH-6) is still required, because v3.0 remains a choice.

### Claude's decisions (autonomous)
- **D-05, what "v3.0" means.** The v3.0 rule set is the app's current rules with the bugs that are wrong in both versions fixed:
  - BUG-1: the native-cover cap goes on Factor A, not B. The official 2021 v3 sheet agrees.
  - BUG-2: Factors G and H accept only 0, 2 or 5.
  
  **Why:** D-02 makes v3.0 a real choice for new surveys, so it must not keep a known transcription bug. Since D-04 means there is no real data, fixing it costs nothing.
  - The research must still show that submitted test surveys replayed from a device do not block sync. Either validation does not reject on a recomputed-score mismatch, or the dispatch keeps a replay path.
  - If that cannot be made safe simply, the fallback is: keep a frozen "legacy" path only for identical replays of already-submitted surveys, and record why.
- **D-06, the package's shape** (the researcher confirms or corrects this against the real toolchains):
  - `packages/ibp-domain` is a plain TypeScript npm workspace with no runtime dependencies, containing pure functions only.
  - It exports:
    - the factor keys;
    - the allowed sets per method version;
    - scoring and draft/submit validation per method version;
    - the cas model (v3.2) and the region/stage model (v3.0);
    - the interpretation bands;
    - the sync contract types.
  - It builds to JavaScript with `tsc`, so the NestJS build and the Docker image need no path tricks. Metro must resolve it in the monorepo, and the Jest configs in both workspaces map it.
  - The API image build must copy the package and still keep all mobile dependencies out of the image. CI's Docker smoke test checks that.
- **D-07, parity.** One shared fixture set runs inside the package and covers every factor for both versions: the v1 matrix cases for v3.0, the new v3.2 target cases, and `MAT-VER-01` for dispatch. The API and mobile test suites each run the same fixture through their adapters, which proves that both delegate to the package. `factor_f_group_capped` (the known drift) is resolved in one place.
- **D-08, the v3.2 station model (cas 1–4).**
  - New v3.2 surveys record the cas directly. The observer picks the cas; it is pre-filled from region and stage where that is unambiguous (ADR-003 mapping table).
  - v3.2 surveys carry no `region_version`/`vegetation_stage`.
  - For drafts: an existing draft keeps its version (null means v3.0); nothing is silently re-scored. ADR-003 said drafts would be re-scored under v3.2, but D-02 supersedes that: a draft's version is its creator's choice, v3.0 for legacy drafts. The observer can switch an unsubmitted draft to v3.2, and the form then asks for the cas.
  - The researcher checks how `region_version`/`vegetation_stage` are used in the form, the API and the public map, and proposes the least disruptive shape. The rule stays: one version per survey, and the form follows it.
- **D-09, field changes.**
  - The v3.2 field-definition changes from the comparison document are implemented only where the app has an input for them: strata heights and diameters (help texts and thresholds), F microhabitat types, G/H/I/J type lists, and so on. Everything else is documented.
  - Help texts come from the French catalogue (`mobile/src/i18n/fr/`), per version.
  - Linear-stand rows (F-5, G-3, CD-6) are recorded as not applicable: the app has no linear stands.
- **D-10, storage.**
  - **Database:** an API migration adds a nullable `ibp_method_version` column to `surveys`, constrained to known values, where null means v3.0. The same for the cas.
  - **Phone:** a SQLite `user_version` migration 3 on mobile (migration 2 exists from 01.9).
  - **Sync:** additive. Installed apps that do not send a version keep working as v3.0.
  - **Public map:** it keeps working, and it shows the version in the survey detail if cheap.
- **D-11, the "/50" display.** `IbpScoreBadge`, `SectorScoreCard` and any other total display switch to `/50`, with the band colours from the package.
- **D-12, tests** (criteria 4–5):
  - RS256: serve a local JWKS from a test key pair and cover valid, expired, wrong-audience and unknown-`kid` tokens against `AuthGuard`. No network.
  - E2E: split `surveys-idempotency.e2e-spec.ts` into submit, visibility, public map, attachments and parcel history. Replace `Date.now()` ids with `randomUUID()`.
  - The whole E2E suite must stay green in both local and MinIO modes.
- **D-13, verification and owner step.** Claude verifies everything:
  - the full local gate and E2E in both modes;
  - native builds in CI;
  - production probes after the deploy: an additive migration, and old clients still sync.
  
  The owner then does one short iPhone check, in simple French and at most 6 steps:
  1. create a survey: the version choice is shown with v3.2 as default;
  2. fill a factor and see the score out of 50;
  3. create a v3.0 survey;
  4. check the existing surveys still open and sync.
- **D-14, docs.**
  - `docs/references/README.md` and `docs/specs/ibp-form-spec.md` say "implemented: v3.2 (v3.0 available per survey)".
  - `docs/technical/ibp-validation-matrix-v2.md` is added (CH-10).
  - The API contract and data contract document `ibp_method_version` and the cas.
  - CLAUDE.md gets the new package in the monorepo table and the key files.
- **D-15, one PR.** One PR for the phase, like 01.9. Deployment is the usual pull-based API image. The DB migration must be additive and pass `migrate.js` with its advisory lock.
</decisions>

<amendments>
## Amendments after research (Claude, 2026-09-26; RESEARCH wins where it had evidence)
- **D-10 amended:** no SQLite migration 3. Method version and cas live in the schemaless `payload_json`, no query filters on them, and `SCHEMA_VERSION` stays 2. The API gets migration 016, which is additive and nullable, with null meaning v3.0. Version comparisons normalise null to v3.0, so a replay of a null row that sends an explicit v3.0 tag is not a conflict.
- **D-08 amended:** v3.2 surveys record `ibp_cas` (1–4) plus a boolean `ibp_cas3_scale`. The flag selects the cas-3 A/G scale for cas 2 within a cas-3 zone, and for lapiaz, dune, peat-bog and *J. thurifera* stands (v3.2 p. 3 "2*", p. 4 footnote, p. 7). The name is always `ibp_cas`, never a bare "cas", because CAS already means compare-and-swap in this codebase.
- **D-03 amended:** the CNPF chart has bands only for the stand score (/35) and the context score (/15), not for the /50 total (p. 24).
  - The /50 total uses a documented `totalBand` with cut-offs at 10/20/30/40, marked for the owner's review.
  - The stand and context sub-scores use the CNPF bands where they are shown.
- **D-05 clarified:** fixing BUG-1 (the cap on A) changes MAT-B-01 under v3.0 (B goes from 2 to 5). `ibp-validation-matrix-v2.md` and a short addendum to ADR-003 must record this.
  - D-05 is safe for replays: validation never compares recomputed scores. The only newly blocked shape is a direct G=1 or H=1, which the form cannot produce. The E2E and unit fixtures that use it move to 2.
- **D-06 clarified:** the package builds to `dist` only for Node at runtime (Docker, `start`, `dev:api`). Metro and Jest read `src`.
  - Package fields: `main` points to `dist`; `types` and `react-native` point to `src`. Both Jest configs map the package name.
  - Never add a `prepare` script: it runs even under `npm ci --ignore-scripts` and breaks the Docker runtime stage.
  - Depend on the package with the version `"*"`, not `workspace:*`.
  - `packages/**` is added to the ci.yml path filters (shared, image, native).
- **D-12 clarified:** tests that fit none of the five features stay in a slimmed `surveys-idempotency.e2e-spec.ts`.
- **Sync invariants to keep:**
  - `/v1/sync` strips fields not on the DTO, so the version and cas must be added to the DTO.
  - `buildSurveyPayloadFromRemote` copies an explicit list of fields, so they must be added there too.
  - The API is deployed before the owner installs the new app build.
- **Owner review items** (end of phase):
  - the /50 total band cut-offs;
  - the home sector average mixing v3.0 and v3.2 surveys (shown with a "méthodes mêlées" note);
  - cas 1 preselected for new v3.2 surveys;
  - new API error codes, handed to 01.9-32 for their French messages.
