<context>
`IbpRulesService` (`api/src/surveys/ibp-rules.service.ts`) and `mobile/src/app/ibp-scoring.ts` are
already pass-through adapters over `evaluateIbp`/`computeRetainedScores` with zero factor-internals
code (phase 01.8, D-06/D-07): they need no edit for this phase. All the real work is in
`packages/ibp-domain`.

The genus codes (34 classes, 33 genera, `Quercus` split into `Quercus_deciduae` /
`Quercus_sempervirens`) must match ADR-002's own label set 1:1, since Phase 6 wires a classifier's
output directly into `genera` — a second, incompatible vocabulary here would break that hand-off
silently.

`readGenusCount` (`rules/common.ts`) is today's single choke point for reading Factor A's count in
both `rules/v3-0.ts` and `rules/v3-2.ts`. Replace it (not add beside it) with
`readFactorAGenusCount(raw, cas)`, returning a `{kind: "count"|"none"|"invalid"}` outcome: `"count"`
from a valid `genera` array (deduplicated, filtered to the station's allowed set) or the legacy
bare number; `"none"` when Factor A carries neither; `"invalid"` when `genera` is present but
malformed (non-array, or an entry not on the CNPF list). Both scorer files pass their own cas
(`null` for v3.0, the resolved `ibp_cas` for v3.2) so the supplementary-genus gate is symmetric.

`FactorOutcome`'s `invalid` variant needs an optional `code`/`message` so a scorer can raise
`factor_a_genus_invalid` instead of the generic `factor_invalid_raw` — extend the type, add an
`INVALID_GENUS` constant next to the existing `INVALID`, and make `evaluate.ts`'s issue-push read
`outcome.code ?? "factor_invalid_raw"` (its one other `{kind:"invalid"}` literal must become the
shared `INVALID` constant so its type still matches).

Migration: `factors` is `JSONB NOT NULL DEFAULT '{}'::jsonb` (`api/migrations/001_init.sql`), so no
column is needed — verify with `psql` that `'5'::jsonb -> 'genera'` and
`'{"native_genus_count":5}'::jsonb -> 'genera'` both return `NULL` (not an error) before writing
the constraint, so it never rejects a legacy row. Follow migration 016's guarded
`NOT VALID` + `VALIDATE` pattern.

Adding migration 018 breaks `migration-016-ibp-method-version.e2e-spec.ts`'s
"was applied ... after 015" assertion (it hardcodes "016 is the last file"): fix it to compare
indices (016 immediately follows 015) instead of assuming 016 is the very last migration.

`POST /v1/sync`'s blocking-error surface: `SurveysService.validateUpsertDraft` throws
`UnprocessableEntityException({message, errors, warnings})` with no `code` field, and
`mapSyncError` (`api/src/surveys/sync-error.utils.ts`) only echoes a `code` when the exception body
has one — so a sync-path validation failure always maps to a generic `http_422`, same as every
other blocking IBP issue today. Test the specific code and message through `POST /surveys` (direct,
whose `422` body's `errors` array carries the message text, matching the existing convention in
`surveys-submit.e2e-spec.ts`), and test only `fatal_error`/`http_status: 422` through `/v1/sync`.
Do not invent new error-surfacing plumbing — this phase is the contract, not an error-handling
rework.
</context>
