# Phase 25.1 Plan 11: Map page and photo pages Summary

The map page (parcel polygons projected with the snapshot's own frame over the basemap, or an SVG
outline on a pale canvas, or a note) and the photo pages (six per page in fixed 255 x 200 cells, in
shooting order, captioned), both pure builders, plus the two snapshot fixes the 25.1-07 spike asked
this plan to make.

## What was built

- `map-section.ts`: `buildMapBlock(data, palette)` gives one block (`id: "map"`, `breakBefore`,
  height about 420 of 840) with four outcomes. No parcel id: heading and `map.noParcel`. Parcel ids
  but no usable geometry (`map` null, no polygon, or no finite point): `map.noOutline` plus the
  escaped ids. With a basemap: the JPEG `<img>` at the frame size, an absolutely positioned SVG of
  the same `viewBox` with one `map-parcel` path per polygon (`ringsToPathD(rings, basemap.frame)`,
  `fill-rule: evenodd` so holes work, palette fill and stroke), a border stroke, the scale bar, the
  north arrow, the parcel list and the source line. Without a basemap: no image, a canvas `<rect>`,
  the frame fitted by `fitFrameToBounds(..., { zoomRange: null })` with the zoom capped at 19, the
  same furniture, and `map.outlineOnly`. A basemap whose data URI is not a well-formed
  `data:image/jpeg;base64,` string is not inlined; the page falls back to the outline.
- Scale bar: label baseline 12 above the panel top, line 24 below it, so the label is 12 units over
  the line (the spike's collision is fixed, a test asserts at least 8). Ticks and line are SVG strokes.
  A bar longer than half the frame is dropped (tiny parcels or odd zoom).
- `photos-section.ts`: `PHOTOS_PER_PAGE = 6`, `PHOTO_CELL = { 255, 200 }`, `buildPhotoBlocks`
  (blocks `photos-1`, `photos-2`, ..., each `breakBefore`, heading and notes on the first, about 715
  of 840 for a full first page). Each image is fitted inside the cell keeping its ratio with explicit
  `width`/`height` (800 x 600 gives 255 x 191), centred by absolute offsets; an unusable size falls
  back to the cell. A photo whose data URI is not a JPEG data URI is not inlined and counts as
  unavailable.
- `map-snapshot.ts` (plan 02 file, edit allowed by the coordinator): `withoutSprite`; a `file://`
  composite style is read, parsed, stripped of `sprite` and handed to `createImage` as a JSON string
  (falls back to the URI if unreadable); the snapshot PNG is deleted once the JPEG is made, also on a
  failed conversion and when a snapshot settles after the timeout. `https` style URLs are unchanged.
  `kind` already existed (plan 25.1-07); the caller must pass it.
- 55 new tests: 33 for the map section, 22 for the photo pages; 9 more in `map-snapshot.test.ts`.

## Decisions on the 25.1-07 findings

1. **iOS sprite:** fixed in `takeBasemapJpeg` (above), not in the section builders.
2. **Snapshot PNG left in Documents:** deleted in `takeBasemapJpeg`.
3. **`kind` to `takeBasemapJpeg` (12 s online, 8 s offline):** the function already takes it; the
   caller in the loader (plan 25.1-12/15) MUST pass `choice.kind`.
4. **"Fond de carte : IGN" caption versus the native iOS box:** printed on every basemap, on both
   platforms. Reason: the iOS box "Source : IGN" comes from the `attribution` of the cadastre raster
   source that `withCadastre` adds, so it exists only with the offline style; an online snapshot
   (plain Plan IGN style) carries no such box. A line that depends on the platform and the basemap
   kind would need the kind inside `ExportMap`, and an attribution that is sometimes missing is worse
   than one that is sometimes repeated. It is not printed without a basemap (nothing from the IGN is
   drawn then).
5. **Online coloured Plan IGN without cadastre versus offline map with cadastre:** left as is. The
   parcels are drawn by the SVG overlay in both cases, so the cadastre raster adds nothing the
   reader needs, and unifying them would add a style fetch and a second failure mode to the online
   path. The difference is only the basemap look; the owner can ask for a unified look later (fetch
   the style, `withCadastre`, `withoutSprite`, pass the JSON for the online kind too).
6. **Scale-bar label:** moved above its line (fix above).
7. **No CSS columns, no 1 px filled divs:** none used; canvas, border and scale bar are SVG shapes
   and strokes, photo rows are `display: flex` with fixed widths, a test checks the CSS.

**2. [Rule 2 - Security] Data URI validation in both sections**
- **Found during:** Task 1 and 2 (threat T-25.1-03)
- **Issue:** the plan only asks for `data:` URIs; a malformed string would break out of the `src` attribute
- **Fix:** a basemap or photo is inlined only if it matches `^data:image/jpeg;base64,[A-Za-z0-9+/]+={0,2}$`; others fall back (outline) or count as unavailable
- **Files modified:** `map-section.ts`, `photos-section.ts`

**3. [Rule 1 - Bug] Lint** - a useless regex escape in a test, fixed in 60820c71.

## Notes for the next plans

- The map block and each photo block carry `breakBefore: true` and height; the page packer must give
  each its own page. Frame width 515 and cell width 255 assume 40 units of side margin (595 - 515 = 80).
- `ExportMap.basemap.frame` must be the frame the snapshot was taken with (`takeBasemapJpeg` returns
  it); the overlay is projected with it. `ExportMap.frameSize` is used for the outline only.
- Class prefixes: `map-`, `photos-`. CSS functions `mapSectionCss(palette)`, `photosSectionCss(palette)`
  must both be concatenated into the document style by plan 25.1-13.
- The fonts `Jost-SemiBold` and `Jost-Regular` are used in SVG `<text>` through the `font-family` attribute.
- Plan 15 defines `photos.total` as the number of photo attachments and `unavailable` as non-local
  plus failed; the cap note is `total - items - unavailable > 0`, shown with `items.length`.
- Not verified on a device: the page is rendered from string tests only. The absolute-position
  img plus SVG overlay is the technique the spike measured on iOS and Android.
