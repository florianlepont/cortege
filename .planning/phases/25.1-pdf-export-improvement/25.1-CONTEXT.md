# Phase 25.1: PDF Export Improvement - Context

**Gathered:** 2026-10-10
**Status:** Ready for planning

<domain>
## Phase Boundary

The on-device PDF export of a survey (Phase 19, `mobile/src/app/survey-pdf-export.ts`) is rebuilt so it carries the same information as the official CNPF IBP survey sheet (fiche de relevé), presented in the brand finish, with photos, a parcel map over a basemap and the parcel trend. Still generated on the phone, offline, shared through the OS share sheet. Not a new export channel, not an API change.

Today's PDF: an identity table, the total /50 line and one class label per factor, in plain system styling.

</domain>

<decisions>
## Implementation Decisions

### Content (fidelity to the CNPF sheet)
- **D-01:** The PDF reproduces the information of the official IBP survey sheet, "en plus beau". Each factor A-J shows the raw observations entered in the app (genera, cover percentages, deadwood, etc.), the selected class and the retained points (`score_points`, 0-5), in the order of the official sheet for the survey's method version.
- **D-02:** Subtotals: stand and management /35 and context /15, plus total /50, with the colour bands from `@cortege/ibp-domain` (`standBand`, `contextBand`, `totalBand`). No local band logic.
- **D-03:** Method context is printed per version: v3.2 shows `ibp_cas` (and `ibp_cas3_scale` when CAS 3); v3.0 shows region version and vegetation stage.
- **D-04:** Identity block kept (site, parcels, observation year, version number, date, method), extended with whatever the sheet header carries.

### Details missing from storage (owner decision 2026-10-10, after research)
- **D-12:** To reach the fidelity of D-01, the app now also stores the details it only counted before and the PDF prints them: the strata tiles of factor B, the aquatic and rocky habitat types of I and J, the dendromicrohabitat groups of F and the evidence of factor H (exact list and field names set by the research in `25.1-RESEARCH.md`). This touches data entry and local storage (payload fields, no SQLite migration unless the research shows one is needed) and the sync wire types only if the server must keep them; the planner decides, keeping v3.0 and v3.2 scoring untouched (`@cortege/ibp-domain` rules do not change). Surveys saved before this phase simply print what they have, without placeholders.
- **D-13:** Parcel history for the trend is cached on the device in `local_meta` (key `parcel_history:<ID>`, written by `useParcelSurveyHistory`, purged by `clearLocalIbpData`), including other members' surveys already visible in the app, so the trend prints offline. No SQLite migration.

### Photos and parcel outline
- **D-05:** All the survey's photos are included, resized and compressed (inlined in the HTML), on dedicated pages in shooting order. Not grouped by factor: the app links no photo to a factor and the owner chose not to add that link (2026-10-10, after research). The planner measures PDF weight and generation time on a phone and may set a cap if needed (Claude's discretion on the cap).
- **D-06:** Parcel map: the parcel polygons over a MapLibre basemap snapshot (owner decision 2026-10-10, reversing the first choice of an outline only), with scale and north arrow. The snapshot uses the map style and offline packs already in the app (`mobile/src/map/offline-packs.ts`). Fallback when no basemap tiles are available offline: the vector SVG outline without basemap, so the export never fails or blocks. The research must establish how to take a native MapLibre snapshot (`@maplibre/maplibre-react-native` 11) and embed it.
- **D-06b:** Parcel trend (owner decision 2026-10-10): the PDF includes the trend card of the parcel, the curve of totals cut between methods, and the per-factor changes against the previous survey, reusing `mobile/src/app/parcel-history.ts` and `trend-geometry.ts`, drawn as SVG. The history needs data not always present offline: use what is cached on the device and omit the section with a short note when the parcel has no earlier survey or the history cannot be read offline. The export never waits on the network.

### Brand finish
- **D-07:** Full charter: logo (`mobile/assets/logo-app.png`), charter fonts (`mobile/assets/fonts`), band colours, a factor chart in SVG, header and footer on every page. Reference: `docs/design/charte-graphique-etats-sauvages-spec.md`. Print is always light, so no dark variant. The hex-literal ESLint rule applies: colours come from the allowed token files.
- **D-08:** All text from the French catalogue (`fr.surveyExport`), no em dash (U+2014); the current `unknown: "—"` placeholder must go with it if the catalogue check requires.

### Versions and states
- **D-09:** Both v3.0 and v3.2 are rendered with their own factor labels and context; tests cover both.
- **D-10:** Draft (not submitted) surveys can be exported: a "Brouillon, non soumis" banner plus a light watermark on every page, and missing factors clearly marked.
- **D-11:** The shared file gets a readable name: `Cortege-IBP-<site>-<year>.pdf`, with a `-brouillon` suffix for drafts (the expo-print random name is replaced by a copy/move to that name).

### Claude's Discretion
- Photo cap and compression settings, page breaks, factor chart style, exact page layout (A4), how to name the file when site or year is unknown.

</decisions>

<code_context>
## Existing Code Insights

### Reusable Assets
- `buildSurveyExportHtml` is a pure, unit-tested HTML builder: extend it, keep it free of native dependencies.
- `PhotosStrip`, `AttachmentPhotoPreview`, `ParcelMapCard`, `ScoreBreakdown` in `mobile/src/screens/survey-detail/`: show where photo and parcel data already come from on screen.
- `useSurveyDetailData` for the data shared by the detail sub-pages.

### Established Patterns
- Catalogue-only text, `escapeHtml` on every value, no network call during export.
- Colours only from the token files; static builders in `app/visual-tokens.ts`.
- Domain rules only from `@cortege/ibp-domain` (bands, labels), never re-implemented.

### Integration Points
- `SurveyExportData` grows (raw observations, photos, parcel geometry, draft flag); the call site in `SurveyDetailScreen.tsx` fills it. Keep the screen under the 400-line cap (`structure.test.ts`) by moving the data assembly into a helper.

</code_context>
