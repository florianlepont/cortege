<context>
`packages/ibp-domain`, `api/src/surveys/ibp-rules.service.ts` and `mobile/src/app/ibp-scoring.ts`
need no change: Phase 5 already made the genus-list shape a first-class scored input on both rule
versions, and both server/mobile adapters are already thin pass-throughs (phase 01.8). All the work
here is mobile UI, a new `mobile/src/recognition/` module, and the still-missing Factor A form
wiring Phase 5 deliberately left to this phase.

`FactorChipsInput` cannot be reused as-is for the genus list: it derives a *count* from its
selection and reconstructs "the first N options" on reopen, which would show the wrong genera on a
real list. `FactorGenusListInput` is a sibling component with the same visual language
(`FactorInputShell` + `AppChoiceChip`), controlled by the actual genus codes (comma-joined into the
same `FactorField.value: string` channel every other FactorInput variant already uses).

The model artifact and a real Android device are both unreachable from this container - see
06-CONTEXT.md's decisions. This plan builds every part of the feature that does not require either,
and makes the two gaps impossible to miss (a `README.md` next to the placeholder asset, this
phase's docs, the ROADMAP entry, the PR description).
</context>
