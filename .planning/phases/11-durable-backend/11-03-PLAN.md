<objective>
Prove and document that a fresh database and production reach the same schema version through one
documented path (`npm run migrate:api`), and that a deliberately failed migration leaves the
schema unchanged rather than half-applied.
</objective>

<tasks>

<task type="auto">
  <name>Task 1: Read the existing migration runner</name>
  <action>
    Read `api/scripts/migrate.js`. Confirm it already: takes a session advisory lock, tracks
    applied files in `schema_migrations`, and wraps each file's SQL plus its bookkeeping insert in
    one `BEGIN ... COMMIT` with a `catch` that issues `ROLLBACK` on any failure.
  </action>
</task>

<task type="auto">
  <name>Task 2: Prove atomicity with a deliberately broken migration</name>
  <action>
    Against a scratch database with migrations 001-016 already applied, add a temporary
    `017_test_deliberately_broken.sql` (a valid `CREATE TABLE` followed by a call to a
    non-existent function), run `node scripts/migrate.js`, and record: exit code, whether the
    valid statement's table exists afterwards, and the exact `schema_migrations` row count.
    Remove the temporary file immediately after (never committed) and confirm a subsequent run
    reports "up to date" with no manual cleanup.
  </action>
  <verify>
    Non-zero exit code; `to_regclass('public.test_atomicity_marker')` is NULL after the failed
    run; `schema_migrations` still has exactly the 16 prior rows, no 17th; re-running after
    removing the broken file succeeds cleanly.
  </verify>
</task>

<task type="auto">
  <name>Task 3: Document the guarantee</name>
  <action>
    Write `api/migrations/README.md`: the one documented path every environment uses, and the
    atomicity guarantee with a description of exactly what was verified in Task 2.
  </action>
</task>

</tasks>
