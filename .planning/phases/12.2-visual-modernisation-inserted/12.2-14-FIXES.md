## Row scores and search Annuler (found while preparing the batch 2 iPhone check)

Two follow-up fixes, one commit each.

### 6. Score rings stay dashed until a survey is opened (390dcd2)

- **Found:** after a fresh launch, submitted rows of Mes Relevés and of the search page showed the dashed "no score" ring until that survey had been opened once. The row score was read only from the `surveyDetails` cache, which the survey detail fills when a survey opens. The stored payload (`local_surveys.payload_json`) already holds `scores.ibp_total` for every survey the pull applied (`buildSurveyPayloadFromRemote` copies `scores`).
- **Changed:** `listLocalSurveys` (`storage/surveys.ts`) selects one more computed column, `ibp_total`, with SQLite's `json_extract(payload_json, '$.scores.ibp_total')`. It runs inside SQLite, only for rows with `status = 'submitted'` (the CASE skips the others), only when `json_valid(payload_json)` and `json_type` is integer or real, so a missing payload, broken JSON, a text or null total all give null. The raw payload is still never selected and there is no `JSON.parse` in JS, so the migration-2 intent (`payload_completion`) holds; no new column and no migration were needed (so no `PRAGMA user_version` change). `LocalSurvey.ibp_total?: number | null` is the new field (optional: the objects the write functions return do not carry it). New helper `resolveRowScore(survey, surveyDetails)` (`screens/survey-list/row-score.ts`): a loaded detail wins (fresher), else the stored total, else null. Mes Relevés and the search page call it; Accueil's "Mes relevés récents" can import it. Drafts still show the completion arc and a submitted survey without a score the dashed ring (`SurveyRow` is unchanged).
- **Tested:** `surveys.completion.sqlite.test.ts` (real SQL): the total of a survey pulled from the server, a total of 0 kept, null for no scores, no key, a text value, a null value, no payload and broken JSON, null for a draft whose payload holds an old total, and the 500-survey test still asserts zero `JSON.parse` calls, no `payload_json` in the result and that the SQL goes through `json_extract`. `row-score.test.ts` (priority detail, then stored, then null; 0 kept). `SurveyListScreen.test.tsx` and `SurveySearchScreen.test.tsx` assert the `score` each row receives with and without a loaded detail. Render-count and the other sqlite suites stay green.
- **Known limit:** a survey created and submitted on this phone has no `scores` in its payload until the next pull applies the server copy (or until it is opened, which fills the detail cache), so its ring is dashed in between, as before. Also `json_extract` reads the whole payload of each submitted row in the engine on every list read; it is cheap for dozens of surveys, but a precomputed column in the migration-2 manner is the fallback if the list ever feels slow with hundreds of submitted surveys.
- **Device only:** rings present at the first frame after a cold launch (no dashed flash), and the list read time with a real, large local database.
